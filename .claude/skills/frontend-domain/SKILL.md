# Бізнес-контекст на фронтенді

**Джерело правди — бекенд.** `../api-med-scheduler/docs/domain.md` + контролер і сервіси ендпоінту. Фронт правила лише **віддзеркалює** як підказки й блокування; остаточно вирішує сервер. Якщо правила, потрібного для UI, у `domain.md` немає — не вигадуй його: перевір код бекенду або спитай користувача.

## 1. Глосарій (не плутати)

| Укр. (UI) | Англ. (код / API) | Суть | Пастка |
|---|---|---|---|
| Заняття | `Lesson` | одна подія: `date`, `duration` (хв, ≥ 5), `note`, `visibility` | «перенесення» немає — редагують `date` |
| Група занять (курс, серія) | `LessonsGroup`, `lessonGroupId` | зв'язка серії / пов'язаних занять, **необов'язкова** | ≠ студентська група |
| Студентська група | `StudentGroup`, `studentGroupIds` | академічна група з тегами | ≠ група занять |
| Тег групи | `GroupTag` | форма навчання, спеціальність | фільтр `groupTagIds` |
| Кафедра | `Department` | 0..N на заняття (`departmentIds`) | |
| Завідувач | `headTeacherId` (кафедра) / `teacher.headOfDepartmentId` (користувач) | редагує заняття своєї кафедри | |
| Староста | `student.isGroupMonitor` | | |
| Викладач | `Teacher`, `teacherIds` | профіль 1:1 до user | **`teacherId ≠ userId`** |
| Роль / дозвіл | `Role` (`rolePriority`) / `Permission` | | |

Один користувач може мати профіль викладача **і** студента, або жодного.

## 2. Три механізми доступу → UI

| Механізм | Що вирішує на бекенді | Як виражається на фронті |
|---|---|---|
| **Дозвіл** (`Permission`) | чи відкритий ендпоінт (`@Permissions(...)`, OR; `admin` проходить завжди) | `usePermissions().hasAny([...ті ж дозволи, Permission.ADMIN])` — **ADMIN додається вручну**, бо `hasAny` байпасу не має. Набори — константи `READ_PERMISSIONS` / `MANAGE_PERMISSIONS` угорі секції; ті самі набори в `sidebar.config.ts` `isVisible` |
| **Ієрархія ролей** | над ким дозволено діяти (`canManageUser` / `canManageRole` за `rolePriority`) | прапорець `canManage` з відповіді `/users`, `/roles` → `Table rowLock` (`isLocked` + `reason`): рядок видно, дії вимкнено, замочок з поясненням. Ранги на клієнті **не рахуй** |
| **Участь у занятті** (домен викладачів) | редагування й видимість занять; дозволи тут **не діють** | навігація — за профілем (`user.teacher`, `user.student`, `teacher.headOfDepartmentId`); дії над заняттям — за `lesson.canEdit` з відповіді |
| **Адмін-панель занять** | `/admin/lessons*` за `read_lessons` / `manage_lessons` | `hasAny([READ_LESSONS, MANAGE_LESSONS, ADMIN])` для перегляду; редагування лише з `MANAGE_LESSONS` / `ADMIN`; правило кафедр не застосовується |

Правила відображення:
- Прихований пункт сайдбару **не закриває маршрут**: секція сама перевіряє доступ і показує заглушку `noAccess`.
- Недоступне ховаємо лише тоді, коли користувачу воно в принципі нерелевантне (немає профілю / дозволу). Якщо сутність видно, але діяти над нею не можна — показуємо й блокуємо з поясненням (`rowLock`, вимкнена кнопка + `hint`).
- Свій акаунт змінюється лише через `/auth/me` (ProfileModal), не через таблицю користувачів.

## 3. Видимість занять

| `visibility` | Хто бачить |
|---|---|
| `all` | усі, включно з анонімами `/schedule` |
| `involved` | викладачі заняття, завідувачі його кафедр, студенти його груп |

Для решти приховане заняття **не існує**: 404, а не 403. У UI 404 по заняттю — «не знайдено або приховано», а не «немає доступу». Для видимого, але чужого — 403.

Заняття несе назви для показу (`teachers`, `studentGroups`, `departments`, `lessonGroupName`) — довідники для відображення не потрібні, лише для селектів.

## 4. Погляди занять (`LESSONS_VIEWS`)

| Погляд | Маршрут | Хто | Джерело | Створення |
|---|---|---|---|---|
| `study` | `/dashboard/study` | є `student` | `/lessons/my?scope=studying` | — |
| `teaching` | `/dashboard/teaching` | є `teacher` | `/lessons/my?scope=teaching` | так |
| `department` | `/dashboard/teaching?tab=department` | завідувач | `/lessons/my?scope=department` | так |
| `all` | `/dashboard/lessons` | усі з токеном | `/lessons/list` | — |
| `admin` | `/dashboard/admin/lessons` | `read_lessons` / `manage_lessons` | `/admin/lessons` | редагування з `manage_lessons` |

Новий погляд = запис у `LESSONS_VIEWS` (джерело, scope, фільтри, `canCreate`), а не умови в компонентах.

## 5. Правила, що віддзеркалюються у формах

Створення / редагування заняття в домені викладачів (`createLessonSchema` у `LessonForm/lesson.scheme.ts`):
- автор **завжди** серед `teacherIds` → `MultiSelect lockedValues` («(you)»);
- хоча б один викладач;
- кафедри — лише кафедри обраних викладачів; кафедри, що вже є в занятті, лишаються допустимими; в адмінці обмеження немає (`restrictDepartments: false`);
- група занять необов'язкова; у наявну групу кладуть лише «свої» (`/lessons-groups/my`, бекенд перевіряє `canUseGroup`);
- серія: дати будує клієнт (`buildSeriesDates`), ≤ 200, сервер створює рівно ці дати.

Групи занять: створює викладач; класти заняття — автор групи або член її кафедри; перейменувати / видалити — автор або завідувач її кафедри.

Правило, що залежить від даних (довідник викладачів, поточне заняття), — **фабрика схеми** з контекстом, а не перевірка в `onSubmit`.

## 6. Процедура: нова бізнес-фіча

1. Знайди правило в `domain.md` (сутність, таблиця доступу, ендпоінт у «Карті ендпоінтів»).
2. Відкрий контролер ендпоінту: який guard / `@Permissions`, чи це домен викладачів (`@LessonActor()`), які поля відповіді вже несуть рішення (`canEdit`, `canManage`).
3. Визнач механізм (розділ 2) і відповідний UI-засіб. Якщо відповідь бекенду вже містить прапорець — використовуй його, не дублюй логіку.
4. Валідацію, яку бекенд поверне як 400, віддзеркаль у zod-схемі (фабрика, якщо залежить від даних).
5. Помилки сервера показуй через `getErrorMessage` (тексти бекенду англійською, без перекладу).
6. Тексти описів (`description`, `hint`) пояснюють реальну поведінку з `domain.md`, нічого не обіцяючи понад неї.
7. Якщо фіча змінює контракт або правило — зміни в бекенді йдуть першими, `domain.md` оновлюється в репозиторії API, а розділ CLAUDE.md фронту — тут.

## 7. Чекліст

- [ ] Правило знайдено в `domain.md` або коді бекенду, а не припущено.
- [ ] `hasAny` містить ті самі дозволи, що й `@Permissions` ендпоінту, **плюс** `ADMIN`.
- [ ] Для users / roles — `canManage` з відповіді, не власний розрахунок рангу.
- [ ] Для занять — `canEdit` і профіль, без `Permission` (крім адмінки).
- [ ] Секція перевіряє доступ сама, незалежно від сайдбару.
- [ ] `teacherIds` — це `teachers.id`.
- [ ] 404 прихованого заняття не подається як «немає доступу».
